Short answer: yes, according to the published literature, and 240 is the smallest n for which it works. I couldn't obtain the actual partition, though, so I can't hand you X.

Why it's equivalent to a polynomial problem. X and Y have equal i-th power sums for i = 0..9 exactly when f(x) = Σ_{a∈X} x^a − Σ_{b∈Y} x^b is divisible by (x−1)^10. That makes f a ±1-coefficient "Littlewood polynomial of order 10."

  • Shifting from {1..240} to {0..239} changes nothing, since a shift only mixes in lower power sums.
  • Thue–Morse (split by parity of binary digit sum) needs 2^10 = 1024 numbers.
  • A necessary condition is that n be divisible by 16, the smallest power of 2 above 10. 240 = 16·15 meets it.

DP is dynamic programming. Here it means two table-building passes.

  1. Block table. For each order t, it lists every length obtainable as an expanded product of the known building blocks with orders summing to t. It is built up from smaller orders: for each block (n, m), lengths at order t are n times lengths at order t − m. By the paper's Multiplication rule, each such product is a valid polynomial of that order.
  1. Coin table. Fix a target order M and take as "coins" all block lengths of order ≥ M and length ≤ 2^(M−1). The question is whether 2^(M−1) is a sum of coins, with repeats allowed. That suffices because the paper's Addition rule lets any such blocks be joined end to end into one polynomial of order ≥ M.
  • It marks every total from 0 to 2^(M−1) that some combination of coins can reach. In practice this is a bit-array where bit x means "x is reachable", updated by OR-ing in shifted copies for each coin.
  • Everything is first divided by the common power of 2, which keeps the array to about 2²³ bits.

Because the table covers every total, "not representable" is exhaustive for the given block list, with any number of blocks.

  • Fix a modulus M. Since xˢ ≡ x^(s mod M) modulo xᴹ − 1, reducing f modulo xᴹ − 1 gives F(x) = Σ_{r<M} d_r xʳ. Here d_r = #{s ∈ X : s ≡ r} − #{s ∈ Y : s ≡ r}.

The reduction. Write f = S + T, with S = (f + f*)/2 and T = (f − f*)/2, where f* is f reversed.

  • Each mirror pair {i, n−1−i} contributes to exactly one of S and T. So both have coefficients in {0, ±1}, on complementary supports.
  • S is unchanged by reversal and T changes sign.
  • If S = (x−1)ᵏG with G(1) ≠ 0, then S = x^{n−1}S(1/x) forces G(x) = (−1)ᵏx^{n−1−k}G(1/x). At x = 1 this gives (−1)ᵏ = 1, so the order of S at 1 is even. The same argument shows the order of T is odd.
  • Two orders of different parity can't cancel, so ord f = min(ord S, ord T).
  • Consequence for any witness of exact order m: its (−1)ᵐ-symmetric part has exact order m, and the other part has order at least m + 1. This bears on the Symmetry Conjecture, though it doesn't prove it.

Yes, I think I found the slowdown and a fix, using a standard trick from integer programming. I tested the idea in Python but not in Mathematica.

Why it's slow. Each case is linear equations in integer unknowns: the 27 class counts c, the 26 lattice coefficients z, and the fixed mod-9 sums. The solver first relaxes to real numbers, and over the reals the lattice condition says nothing, because any real vector is some real combination of the basis. So the relaxation looks feasible everywhere and the solver branches blindly. I imitated a weak solver with a deliberately naive branch-and-bound. On this formulation it gave up after 3,000 nodes on each case I tried, without a verdict.

The fix. This is a reformulation from Aardal, Hurkens and Lenstra (2000) for integer programs with equality constraints. Write every integer solution of the equations as x₀ + y·K, where K is an LLL-reduced basis of the integer solutions of the homogeneous system. Here that basis has 18 vectors. The only constraints left are 0 ≤ c ≤ class size, and the solver branches on the 18 coefficients y. Because the basis is reduced, each branch cuts the box along a direction where it is thin, so infeasibility shows up after a few branches. With the same naive branch-and-bound:

  • all 2025 cases came back infeasible;
  • each needed about 9 branch nodes on average, 67 at most, about 58 s in total;
  • the n = 528 control came back feasible after 5 nodes.

      Do[v[[Mod[t + k, M] + 1]] += e[[t + 1]], {t, 0, m}]; v], {k, 0, M - 1}];
